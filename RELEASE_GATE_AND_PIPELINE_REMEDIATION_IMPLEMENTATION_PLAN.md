# BC250 LLM MODE — Release Gate and Pipeline Remediation Plan

## Closing the audited enforcement gaps before C4/C5/C6/C8

**Status:** Proposed execution authority

**Starting checkpoint:** `a649ac7` on `main`; version `0.9.0.dev0`; database schema v10; authoritative collection 1064; focused release suite 95/95; C0, C1, C2, C3, and C7 recorded as developer-executable complete.

**Purpose:** repair the concrete release-control defects found during the post-C7 audit before any hardware qualification, independent review, human acceptance, or release publication is treated as qualifying evidence.

**Scope:** release-state authority, evidence schema/validation, artifact and commit binding, release tooling, SBOM/attestation verification, GitHub workflow hardening, documentation truth, and the transition into the externally gated C4/C5/C6/C8 milestones.

**Non-goal:** this plan does not fabricate or substitute for physical BC250 evidence, security-review approval, non-developer acceptance, owner authorization, or a public release. It prepares trustworthy mechanisms for collecting and evaluating those events.

---

## 1. Current verdict

C7 is complete for developer scope: policy v2 classifies every known capability, model conversion is `DEFERRED_NOT_ADVERTISED`, backup/restore publication is mandatory and implemented, and the unclassified-limitation check exists.

C3’s implementation scaffold is present, but its full exit gate is not closed:

- only `actions/checkout` is pinned to a full commit SHA;
- setup/upload/download/attestation actions remain mutable tag references;
- attestations are generated by workflow shape but not verified afterward;
- the release workflow does not emit the complete candidate inventory/release manifest it claims;
- the publish step is deliberately a refusal placeholder;
- live CI attestation/signing/publication evidence does not exist.

The release-gate layer also contains release-blocking correctness flaws:

1. `ReleaseState(..., evidence_satisfied=True)` can be instantiated publicly and return `may_tag_1_0_0() == True` without evaluator-produced evidence.
2. `evaluate_release()` permits `source_commit=None`; a complete synthetic evidence set can qualify without source binding.
3. Evidence records missing `source_commit`, `evidence_id`, `issuer`, `artifact_subjects`, or `signature_or_attestation_reference` are currently accepted.
4. Signature/attestation references are treated as unverified strings.
5. `tools.release evaluate --artifacts` parses but ignores the artifact directory.
6. `tools.release verify` inventories files but does not compare them with manifest subjects.
7. Evidence may contain a credential-like value under an innocuous key because secret checks focus on key names.
8. The workflow’s SBOM verification checks only that some SHA-256 exists, not that the validated SBOM subject equals the actual wheel digest.
9. The release workflow is not bound to a protected tag/ref and does not run the authoritative release evaluator over the produced artifacts/evidence.
10. Repository documentation calls C3 complete while explicitly listing C3 action-pinning and live-attestation work as pending.

These issues are P0/P1 release blockers. C4 hardware runs must not begin until the evidence contract and artifact-binding fixes are complete; otherwise expensive physical evidence could be structurally invalid.

## 2. Execution rules

### 2.1 Session discipline

Each remediation session must:

1. select one milestone or bounded sub-slice;
2. add the first failing test before production changes;
3. state which old behavior is being deleted, deprecated, or migrated;
4. preserve application runtime behavior outside release tooling;
5. run focused release tests plus the reconciled default suite;
6. update `AGENTS.md` with exact evidence and remaining blockers;
7. stop at the milestone exit gate.

### 2.2 Safety rules

- Do not tag, push, publish, configure a trusted publisher, or alter repository environments without explicit owner authorization.
- Do not add fake PASS evidence or example records to `release/evidence/`.
- Do not treat a unit-test fixture signature as a production attestation.
- Do not weaken the release policy to make a test pass.
- Do not silently accept unknown evidence fields or kinds.
- Do not rebuild artifacts after qualification or approval.
- Do not use local untracked files in release builds.
- Do not delete owner-controlled untracked files.
- Do not run C4/C5/C6 evidence collection against artifacts produced before the remediation gate is complete.

### 2.3 Compatibility policy

The release manifest and evidence schemas are pre-1.0 internal contracts. Prefer a clean schema advancement over perpetuating an unsafe compatibility path:

- preserve read support for manifest v2 only if an actual consumer is identified;
- v2 records must never qualify v3 release decisions without an explicit, fail-closed migration/validation step;
- do not preserve the public `evidence_satisfied` constructor field as an authority;
- CLI output changes should remain machine-versioned and documented.

## 3. Required outcomes

The remediation is complete only when:

- no public constructor or mutable boolean can create a tag-eligible state;
- only `evaluate_release()` can produce an eligible decision;
- evaluator eligibility requires a full source commit and exact artifact inventory;
- every evidence record has all mandatory fields with bounded types and values;
- every accepted evidence artifact subject matches the actual candidate inventory;
- evidence claiming signing/attestation is accepted only after cryptographic verification;
- `tools.release evaluate`, `manifest`, and `verify` are end-to-end truthful;
- SBOM validation compares its subject to the exact wheel digest and checks required components;
- all GitHub Actions references are full reviewed SHAs;
- the release workflow generates, verifies, and attests the exact complete release set;
- post-attestation verification succeeds before approval/publish;
- the workflow refuses wrong version, wrong commit/ref, wrong digest, missing evidence, or unprotected invocation;
- docs describe C3 as fully complete only after these requirements are met;
- the evaluator still returns false because C4/C5/C6/C8 evidence remains genuinely pending.

## 4. Target authority model

### 4.1 One eligibility authority

`ReleaseDecision` returned by `evaluate_release()` is the sole authority:

```text
ReleasePolicyV2/V3
        +
CandidateIdentity {version, source_commit, source_ref, policy_digest}
        +
ArtifactInventory {subjects and content digests}
        +
VerifiedEvidence[]
        │
        ▼
evaluate_release(...)
        │
        ├── ReleaseDecision (eligible or blocked)
        └── ReleaseManifestV3.from_decision(...)
```

`ReleaseState` may remain as an informational compatibility/read model, but it must not independently decide tag eligibility.

### 4.2 Candidate identity

Introduce an immutable `CandidateIdentity` containing:

- normalized release candidate version;
- full 40-character lowercase Git commit SHA;
- expected protected ref/tag, where applicable;
- repository identity;
- release policy version and digest;
- database schema version;
- release-manifest schema version.

Validation must refuse:

- missing or abbreviated commit hashes;
- all-zero or malformed hashes;
- versions that do not match package/pyproject metadata;
- final `1.0.0` when the ref is not exactly the approved final tag;
- release candidates launched from an unrelated branch/ref;
- policy snapshot/digest mismatch.

### 4.3 Artifact inventory

Make `ArtifactInventory` a required evaluator input for RC and final release decisions. At minimum it must contain:

- exactly one wheel;
- exactly one sdist;
- checksum document;
- validated SBOM;
- release manifest draft/final as appropriate;
- provenance/attestation subjects or references;
- owned container subjects, if any;
- third-party integration identities in a separate, explicit section.

Every identity is content-digest based. Filenames are labels only.

### 4.4 Verified evidence

Split raw records from verified records:

```text
RawEvidenceRecord      parsed JSON; never qualifies anything
ValidatedEvidence     schema/semantic validation passed
VerifiedEvidence      signature/attestation and subject binding passed
```

Only `VerifiedEvidence` satisfies a release gate. Pure unit tests can construct verified fixtures through a test-only factory unavailable from production imports.

## 6. G0 — audit contract and red tests

### Objective

Turn each confirmed defect into a failing automated gate before changing production code.

### G0.1 Baseline reconciliation

Record:

- current HEAD and branch divergence;
- package/pyproject version;
- database and release policy versions;
- authoritative test collection and focused release count;
- current mutable action references;
- current `ReleaseState` bypass output;
- evidence validator acceptance of missing mandatory fields;
- evaluator result when `source_commit` is omitted;
- release-tooling behavior with a mismatched artifact directory;
- exact untracked-file inventory using current `git status` rather than historical counts.

### G0.2 Mandatory red tests

Add tests proving:

1. Explicitly passing `evidence_satisfied=True` to `ReleaseState` cannot qualify a tag.
2. `evaluate_release()` refuses a missing source commit.
3. It refuses abbreviated, malformed, all-zero, or wrong commits.
4. Evidence missing any required top-level field is rejected.
5. Evidence with empty `artifact_subjects` is rejected for release-required kinds.
6. Evidence with a missing/unverified signature or attestation is rejected.
7. Evidence with a token-like value under an innocuous key is rejected/redacted.
8. Evidence subjects that do not match the candidate inventory are rejected.
9. `--artifacts` is required for RC/final evaluation and actually affects the result.
10. `tools.release verify` fails when any artifact is added, removed, renamed contrary to policy, or content-mutated.
11. The SBOM fails verification when its bound hash is not the wheel’s actual digest.
12. Every workflow `uses:` reference must be a full 40-character SHA.
13. The release workflow must execute the release evaluator and fail on blockers.
14. Attestations must be verified before approval.
15. The release workflow must emit inventory, checksum, SBOM, and manifest files.
16. The publish job cannot rebuild or run when authorization/approval evidence is missing.

### G0.3 Test placement

Recommended files:

```text
tests/test_release_gate_remediation.py
tests/test_release_evidence_v2.py
tests/test_release_artifact_binding.py
tests/test_release_workflow_hardening.py
```

Keep the red tests in the default collection immediately. Do not hide them behind a marker. Work in narrow commits or preserve them on a dedicated reviewed branch if the project requires green main between boundaries.

### G0 exit gate

- Every audit finding fails for the intended reason.
- No unrelated test regresses.
- No production file is changed.
- Baseline wording accurately distinguishes tracked cleanliness from untracked owner files.

Recommended commit:

`test(G0): freeze release-gate and pipeline audit findings`

## 7. G1 — eliminate eligibility bypasses

### Objective

Make the evaluator the only code path capable of returning a tag-eligible decision.

### G1.1 Remove `ReleaseState.evidence_satisfied`

Preferred design:

1. Delete `evidence_satisfied` from the public dataclass.
2. Delete or deprecate `ReleaseState.may_tag_1_0_0()` as an authority.
3. If compatibility requires the method, make it always return false and direct callers to `ReleaseDecision`.
4. Build the release manifest from a `ReleaseDecision` plus candidate/artifact data, not from a standalone `ReleaseState` boolean.
5. Preserve informational fields such as current version, channel, known limitations, and blocking descriptions without granting authority.

Alternative design, only if compatibility requires an affirmative facade method:

- `ReleaseState.from_decision(decision)` is module-private/internal;
- it accepts only a `ReleaseDecision` carrying the evaluator sentinel;
- no public field can set eligibility;
- direct dataclass construction always produces a non-eligible informational state;
- serialization excludes private authority markers.

Do not rely on comments saying a caller “should not” pass a field. Enforce it structurally.

### G1.2 Require `CandidateIdentity`

Change:

```text
evaluate_release(
    evidence,
    candidate: CandidateIdentity,
    artifacts: ArtifactInventory,
    policy=...
)
```

Remove optional `source_commit=None` from release-qualifying paths. A diagnostics-only evaluator may show blockers for an incomplete candidate, but it must hard-code `eligible_for_rc=False` and `eligible_for_1_0_0=False`.

### G1.3 Policy authority

- Use the reviewed policy snapshot/digest matching `release/policy-v2.json` or a new v3 if schema changes require it.
- Reject caller-supplied weaker policies in production tooling.
- Permit custom policies only in explicitly test-only APIs or diagnostics that cannot produce eligibility.
- Derive unavailable and limitation sets from reviewed product state/policy, not caller defaults such as `frozenset()`.
- Ensure every known unavailable capability is classified.
- Ensure every accepted limitation has verified acceptance evidence.

### G1.4 Decision construction

Strengthen `ReleaseDecision`:

- eligible construction remains evaluator-only;
- include candidate identity and inventory digest;
- include policy digest;
- include accepted/rejected evidence IDs and reasons;
- include exact required/observed evidence-kind matrix;
- include no caller-supplied booleans;
- canonical serialization is stable;
- private evaluator marker never serializes.

Python module privacy is not a cryptographic boundary, so release scripts must also verify the serialized decision/manifest against evidence and artifacts rather than trusting an in-memory object from arbitrary code.

### G1.5 Compatibility migration

- Search every `ReleaseState(` and `may_tag_1_0_0` call.
- Migrate release tooling/tests first.
- Keep application user-facing release status read-only and non-authoritative.
- Add an architecture guard preventing new direct eligibility calls outside `release_gate.py` and approved compatibility tests.
- Document manifest schema migration.

### G1 exit gate

- The exact audited constructor bypass is impossible.
- No missing/optional source commit can produce RC/final eligibility.
- Eligibility always names a full candidate commit and policy digest.
- Direct `ReleaseDecision(eligible=True, ...)` remains impossible.
- Current candidate remains blocked with stable reasons.

Recommended commits:

1. `refactor(G1): introduce mandatory candidate identity`
2. `fix(G1): remove public release-state eligibility authority`
3. `test(G1): guard the single evaluator authority`

## 8. G2 — evidence schema v2 and cryptographic verification boundary

### Objective

Make accepted evidence complete, bounded, candidate-bound, artifact-bound, and verifiably issued.

### G2.1 Required top-level fields

Schema v2 must require and validate:

```text
evidence_schema_version
evidence_id
kind
release_candidate_version
source_repository
source_commit
policy_digest
artifact_inventory_digest
artifact_subjects[]
issuer {type, identity}
issued_at
expires_at or explicit null
environment {os, architecture, python, runner/workflow}
result
measurements
attachments[]
verification {mechanism, subject, verifier, verified_at, bundle_digest}
supersedes_evidence_id or explicit null
```

Reject missing, unknown, incorrectly typed, empty, oversized, duplicated, or inconsistent fields. Do not silently default mandatory values.

### G2.2 Kind-specific schemas

Each evidence kind needs its own requirements. Examples:

- `DEFAULT_TEST_SUITE`: collection count, chunk selectors/results, skips, aggregate reconciliation.
- `SLOW_SECURITY_STRESS`: required named suites and iteration counts.
- `CLEAN_WHEEL_SMOKE`: wheel subject, isolated environment, commands/results.
- `SBOM`: SBOM subject and corresponding wheel/sdist subject mapping.
- `BUILD_PROVENANCE`: workflow/repository/ref/commit and artifact subjects.
- `ARTIFACT_ATTESTATION`: verified attestation bundle digest for each required artifact.
- `BACKUP_RESTORE_HARDWARE`: hardware fingerprint, backup/restore IDs, live exchange and inference results.
- `SOAK_TEST`: monotonic duration, threshold-policy digest, incident summary.
- `SECURITY_REVIEW`: findings digest and zero-open-blocker assertion.
- `HUMAN_ACCEPTANCE`: scenario matrix digest and intervention/findings summary.
- `KNOWN_LIMITATION_ACCEPTANCE`: exact capability, classification, policy digest, reviewer/owner approval.
- `RELEASE_APPROVAL`: final candidate/inventory/manifest digests and owner authorization.

One generic PASS string must not satisfy semantically different evidence.

### G2.3 Raw, validated, and verified types

Use separate immutable types:

- `RawEvidenceRecord`: parsed but untrusted mapping.
- `ValidatedEvidenceRecord`: structural and semantic validation complete.
- `VerifiedEvidenceRecord`: signature/attestation verified and subjects matched.

The evaluator accepts only `VerifiedEvidenceRecord`. Production cannot instantiate that type directly without a verifier-produced token/factory. Tests use a private test helper.

### G2.4 Attestation verification adapter

Implement a release-tooling adapter that:

- verifies a downloaded attestation/bundle using the approved platform tooling/library;
- checks repository owner/name, workflow identity, source commit/ref, and artifact subject digest;
- records verifier version and trust-root/reference information;
- returns a bounded verified result;
- rejects missing, malformed, unsigned, wrong-subject, wrong-repository, wrong-workflow, or wrong-commit claims;
- never accepts “sigref” or a URL merely because it is non-empty;
- supports offline verification when required by the release runbook.

The pure package layer consumes a verified receipt; network/process execution remains in repository-only tooling behind typed bounded commands.

### G2.5 Secret and privacy validation

Strengthen checks beyond key-name matching:

- credential/token patterns in string values;
- authorization headers and URL userinfo/query secrets;
- PEM/private-key markers;
- known Hugging Face/API token formats;
- raw prompts/completions and conversation content;
- absolute private paths where policy prohibits them;
- maximum string length, nesting depth, list size, key count, and total encoded bytes.

Prefer field allowlists for signed evidence over broad arbitrary `measurements`. Kind-specific bounded fields reduce false positives and leakage.

### G2.6 Supersession and expiry

- Require non-empty unique evidence IDs.
- A record may supersede only an older record of the same kind/subject scope unless policy explicitly allows otherwise.
- Reject cycles and unknown supersession targets in a candidate evidence set.
- Apply policy maximum age even when `expires_at` is null.
- Hardware, security, and human evidence become invalid after candidate-changing commits.

### G2 exit gate

- Every previously accepted incomplete record is rejected.
- Token-like values under innocuous keys are rejected/redacted.
- Missing or fake attestation references cannot qualify.
- Evidence kinds enforce their semantic payloads.
- Only verified records reach the evaluator.
- Property/fuzz tests prove bounded total behavior over hostile JSON.

Recommended commits:

1. `feat(G2): define evidence schema v2 and kind contracts`
2. `feat(G2): add raw-validation-verification type boundary`
3. `feat(G2): verify attestations and artifact subjects`
4. `test(G2): add secret, bounds, supersession, and fuzz gates`

## 9. G3 — artifact-bound tooling, manifest, and SBOM verification

### Objective

Make the release CLI evaluate and verify the actual candidate files rather than syntactically valid claims about arbitrary digests.

### G3.1 Artifact inventory v2

Extend the inventory with:

- inventory schema version;
- candidate identity;
- canonical sorted subjects;
- inventory digest;
- required artifact-role classification;
- duplicate-role detection;
- exact file count and total bytes;
- generated-at/build workflow identity supplied by verified build context;
- symlink/special-file/oversize refusal retained.

Required roles for the candidate build:

```text
python-wheel
python-sdist
checksums
cyclonedx-sbom
release-manifest
```

Attestation bundles/receipts may be external references or additional subjects according to policy.

### G3.2 Evaluator subject binding

For every evidence kind, define which artifact roles/subjects it must cover. Examples:

- clean-wheel evidence covers the wheel digest;
- SBOM evidence covers both the SBOM digest and its wheel subject;
- build provenance covers wheel, sdist, SBOM, checksums, and manifest;
- artifact attestation covers every publishable subject;
- package publish attestation covers the exact published wheel/sdist;
- release approval covers inventory and release-manifest digests.

An evidence record with valid-looking but unrelated digests must be rejected as `ARTIFACT_SUBJECT_MISMATCH`.

### G3.3 Fix `tools.release evaluate`

- Require `--source-commit` for RC/final evaluation.
- Require `--artifacts` and inventory the directory.
- Require `--policy` or use the exact reviewed snapshot with digest verification.
- Load raw records, validate, cryptographically verify, bind subjects, then evaluate.
- Exit 0 for the explicitly requested eligibility level only; distinguish RC evaluation from final evaluation.
- Send JSON decision to stdout and diagnostics to stderr.
- Refuse evidence I/O errors rather than merely printing them while evaluating remaining records.

### G3.4 Manifest v3

Generate the manifest from an evaluator-produced decision and inventory. Include:

- manifest schema/version;
- candidate identity;
- package/database/policy versions;
- source repository/ref/commit;
- artifact inventory and digest;
- SBOM digest;
- evidence IDs/digests used;
- attestation references/bundle digests;
- accepted limitations;
- rejected evidence summary;
- eligibility state and blocking codes;
- integration/runtime/container identities;
- canonical manifest digest.

A final release manifest must be eligible and final-version consistent. A draft blocked manifest may be generated for diagnostics but must say `release_status=BLOCKED` prominently.

### G3.5 Fix `tools.release verify`

Verification must:

1. parse and validate manifest schema;
2. recompute manifest canonical digest;
3. inventory the supplied artifact directory;
4. compare exact subject names/roles/digests/sizes;
5. validate checksums against files;
6. parse and run `validate_sbom()` with required dependencies;
7. verify SBOM subject equals actual wheel digest;
8. verify provenance/attestation bundles;
9. compare source commit/ref and policy digest;
10. reject missing, extra, changed, duplicate-role, or unsupported artifacts;
11. return nonzero on any mismatch.

Printing a fresh inventory without comparing it to the manifest is not verification.

### G3.6 SBOM improvements

- Parse `pyproject.toml` using the standard TOML parser available in supported Python, not a line-oriented partial parser.
- Include resolved installed versions from the built/verified environment in addition to declared ranges.
- Represent build dependencies separately from runtime dependencies.
- Include Open WebUI image digest and llama.cpp runtime/toolchain identities.
- Use a real generated timestamp/serial for candidate output while preserving deterministic canonicalization through explicit inputs.
- Validate CycloneDX-required fields and component uniqueness.
- Prove no source paths, credentials, or environment secrets appear.

### G3 exit gate

- `--artifacts` is required and used.
- Wrong/missing/extra artifact tests fail closed.
- Evidence subject substitution fails.
- Manifest v3 is decision- and inventory-derived.
- `verify` performs complete checks and returns nonzero on every seeded mismatch.
- SBOM validation compares against the exact built wheel.

Recommended commits:

1. `feat(G3): add candidate-bound artifact inventory v2`
2. `fix(G3): bind evidence evaluation to real artifact subjects`
3. `feat(G3): generate decision-derived release manifest v3`
4. `fix(G3): make release verify perform full integrity checks`
5. `feat(G3): strengthen SBOM generation and validation`

## 10. G4 — Complete and harden the CI/release workflow

**Objective:** turn the existing release workflow from a useful scaffold into a
fully pinned, candidate-bound, build-once, verify-after-attestation pipeline.
The workflow must still refuse publication until C4–C6 evidence exists and the
owner explicitly authorizes C8.

### G4.1 Pin every third-party action

Replace every mutable `uses:` reference with a reviewed, full 40-character
commit SHA. This includes, at minimum:

- `actions/setup-python`;
- `actions/upload-artifact`;
- `actions/download-artifact`;
- `actions/attest-build-provenance`;
- any subsequently introduced signing, cache, release, or publishing action.

For each pin:

1. resolve the official release tag to a commit using the upstream repository;
2. verify the commit belongs to the expected upstream release;
3. record the human-readable release tag in a trailing YAML comment;
4. record the verification date and source in the C3 evidence section;
5. add Dependabot configuration for GitHub Actions so pin updates are proposed
   as reviewed changes without restoring mutable tags.

Do not guess SHAs. If network verification is unavailable, keep the release
workflow blocked and record the exact unresolved action.

### G4.2 Bind workflow invocation to a candidate

Introduce one normalized workflow input model:

- `candidate_version`;
- `candidate_commit` (normally `github.sha` and never user-substituted after
  checkout);
- `candidate_ref`;
- `qualification_level` (`rc` or `final`);
- `publish_authorized` (owner-controlled, relevant only after every evaluator
  gate passes).

Rules:

- pull requests may test tooling but may never attest or publish;
- RC qualification may run from an explicitly selected immutable commit;
- final qualification must run from a protected `vX.Y.Z` tag pointing exactly
  to `candidate_commit`;
- the tag version, `pyproject.toml` version, package `__version__`, changelog
  heading, and evaluator candidate version must agree;
- a moving branch name is never sufficient identity for a final release;
- checkout must not silently merge the candidate with another ref;
- source archives and package artifacts must identify the same source commit.

Until C8, permit a no-publish qualification mode from the current development
version. It must generate a blocked/draft manifest and must never masquerade as
a final `1.0.0` candidate.

### G4.3 `validate-candidate` job

The first job must perform only read-only qualification:

1. checkout the exact candidate commit;
2. verify the expected commit and ref;
3. reject dirty, generated, or untracked build inputs;
4. verify policy snapshot digest and documentation consistency;
5. collect the authoritative test count;
6. run the default suite and explicitly reconciled platform skips;
7. run the 51-test slow battery;
8. run release-gate, release-tooling, workflow, fuzz, and architecture tests;
9. run compile and formatting/diff checks;
10. run the evaluator in pre-build mode, where artifact-dependent evidence is
    expected to remain blocked but policy/source inconsistencies are not.

The job must publish a machine-readable validation report tied to the exact
commit. It must not possess OIDC or package-publishing permissions.

### G4.4 `build-once` job

Build the wheel and sdist exactly once in an isolated environment. Then:

- reject unexpected files in `dist/`;
- verify wheel/sdist metadata and version consistency;
- install and smoke-test the exact wheel;
- build and test installation from the exact sdist;
- generate canonical checksums;
- generate Artifact Inventory v2;
- generate and validate the CycloneDX SBOM against the exact wheel;
- produce a draft manifest with artifact-dependent blockers still visible;
- archive logs separately from releasable artifacts;
- upload one immutable artifact bundle identified by its inventory digest.

No downstream job may rebuild, rename, normalize, recompress, or otherwise
change candidate artifacts.

### G4.5 `verify-artifacts` job

Download the build-once bundle into a clean runner and:

1. reject artifact transport digest changes;
2. run the complete `tools.release verify` path;
3. install the exact wheel with the repository root absent from `sys.path`;
4. initialize a fresh schema and exercise the packaged CLI and operation worker;
5. install from the exact sdist in a separate environment and repeat smoke
   checks;
6. produce artifact-verification evidence whose subjects equal the inventory;
7. rerun evaluation with this new evidence and preserve all remaining blockers.

This job has `contents: read` only and no OIDC/publish credentials.

### G4.6 `attest` and post-attestation verification

The attest job may receive `id-token: write`; no prior job should. It must:

- attest each publishable artifact by content digest;
- attest the SBOM and inventory/manifest bundle separately where supported;
- bind provenance to the repository, workflow identity, source commit, and
  workflow run;
- save the returned attestation references/bundles as immutable outputs;
- never treat action success alone as verification.

A separate verification step or job must download the attestations and verify
them against:

- the expected GitHub repository owner/name;
- the exact workflow identity;
- the candidate source commit;
- each actual artifact digest;
- the expected subject media type and role.

Only successful post-attestation verification may create a verified
`PACKAGE_ATTESTATION` evidence record. If artifact signing is a separate 1.0
requirement, implement the selected signing method here and verify the signature
before creating `PACKAGE_SIGNATURE` evidence. Do not conflate GitHub build
provenance with an artifact signature unless policy explicitly and publicly says
they are equivalent.

### G4.7 Final evaluation and approval environment

After verification:

- construct CandidateIdentity from trusted workflow context;
- inventory the downloaded artifacts again;
- load only validated and cryptographically verified evidence;
- run the authoritative final evaluator;
- generate the final manifest from the resulting decision;
- run complete manifest verification once more;
- require `eligible_for_1_0_0=true` before entering the approval environment.

The approval environment must be configured in repository settings with the
appropriate required reviewer(s). Environment approval is not a substitute for
the evaluator and cannot make a blocked candidate eligible.

### G4.8 Publish exact artifacts only

The publish job must:

- require both final evaluator eligibility and environment approval;
- download the exact previously built artifact bundle;
- repeat digest and manifest verification immediately before upload;
- publish only wheel and sdist roles approved by inventory;
- never rebuild or modify metadata;

## 13. Required test matrix

The executor must implement behavior tests, not only static assertions.

### 13.1 Release-authority tests

- Public `ReleaseState` construction cannot assert eligibility.
- Legacy `evidence_satisfied=True` is rejected or permanently ignored.
- Candidate version without source commit is invalid.
- Candidate commit without source ref/repository identity is invalid for final.
- Policy digest mismatch blocks.
- Unknown policy/evidence/gate/capability enum values block.
- `ReleaseDecision` cannot be directly instantiated as eligible outside the
  evaluator's controlled path.
- RC and final requirements are distinct and deterministic.
- A complete set of validated but unverified records cannot qualify.
- One missing subject, stale record, or wrong candidate blocks exactly once with
  a stable code.

### 13.2 Evidence tests

- Every mandatory envelope field is independently omitted and refused.
- Empty strings, malformed timestamps, bad digests, duplicate IDs, duplicate
  semantic coverage, unknown fields, and oversized records are refused.
- Issuer-role and evidence-kind mismatches are refused.
- Evidence for commit A cannot qualify commit B.
- Evidence for inventory A cannot qualify inventory B.
- Superseded, expired, future-dated, or policy-version-mismatched records fail.
- Attestation references that are merely syntactically valid do not verify.
- Signature/attestation verifier failure, timeout, untrusted identity, wrong
  repository, wrong workflow, and wrong subject all fail closed.
- Secret-like values are detected in nested maps/lists even under benign keys.
- Paths, prompt/conversation text, bearer tokens, hub credentials, gateway
  secrets, private keys, and raw logs are prohibited.
- Stable safe measurements and bounded numeric summaries remain accepted.

### 13.3 Artifact and manifest tests

- Missing, extra, renamed, replaced, truncated, symlink, hardlink-surprise, and
  special-file artifacts are refused as appropriate.
- Same filename/different digest and same digest/different unexpected role are
  both detected.
- Duplicate role and case-normalization collisions fail.
- Inventory canonical digest is deterministic.
- Manifest digest changes with any candidate/evidence/artifact change.
- A draft blocked manifest cannot be mistaken for a final manifest.
- Final manifest generation refuses an ineligible decision.
- SBOM subject must equal the actual wheel digest.
- Missing runtime/build dependencies and duplicate CycloneDX components fail.
- Wheel and sdist versions/metadata must agree with CandidateIdentity.

### 13.4 CLI/tooling tests

- `evaluate` requires and consumes `--artifacts` and `--source-commit`.
- Malformed evidence causes nonzero exit without partial eligibility.
- JSON goes only to stdout; diagnostics go to stderr.
- `manifest` requires evaluator decision and inventory inputs.
- `verify` returns nonzero for every seeded mismatch.
- An exact valid synthetic fixture passes all local tooling.
- Exit-code vocabulary is documented and stable.
- Tools remain repository-only and do not expand the application runtime import
  surface.

### 13.5 Workflow tests

- All action pins satisfy the full-SHA rule.
- Permissions are least privilege per job.
- Candidate commit/ref/version are propagated without mutable substitution.
- Only one build path exists.
- Build outputs are immutable across job boundaries.
- SBOM and provenance verification use actual subjects.
- Evaluator failure prevents approval and publish.
- Approval cannot override evaluator failure.
- PR and ordinary branch events cannot publish.
- Final publish uses exact artifacts and no wildcard expansion.
- External-evidence blockers prevent the real current checkout from publishing.

### 13.6 Regression and platform tests

- Existing 1064-test baseline remains green before count growth is reconciled.
- Existing 95 release-related tests remain green or are deliberately migrated
  with an explicit compatibility decision.
- Existing 51-test slow battery remains green.
- Database schema remains v10 unless a separately justified application-data
  migration is required; release metadata should stay outside runtime SQLite.
- App startup and normal operation must not read release-evidence files.
- Linux-gated backup exchange and tkinter-gated UI skips remain explicit rather
  than silently disappearing.

## 15. Compatibility and migration decisions

### 15.1 `ReleaseState`

Preferred end state: `ReleaseState` is informational only and has no eligibility
method. If compatibility requires keeping `may_tag_1_0_0()`, it must return
`False` unless supplied an opaque evaluator-issued decision token that cannot be
constructed from booleans. A deprecation period may preserve imports, never the
bypass.

### 15.2 Evidence schema

Keep v1 records readable only for diagnostics. They must not satisfy v2 policy
requirements unless a deterministic migration proves all mandatory v2 fields
from trusted source data and the migrated record is re-verified. Never synthesize
issuer, subjects, signatures, or commit bindings.

### 15.3 Policy and manifests

- Keep policy v1/v2 snapshots immutable.
- Add policy v3 only if requirements change; bind all new records to its digest.
- Keep manifest v2 parsable for historical diagnostics but ineligible for a new
  final release.
- Never silently reinterpret an older policy or manifest under newer semantics.

### 15.4 CLI

Breaking changes to repository-only release tooling are acceptable when they
close a security/release bypass. Provide explicit error messages and update the
runbook. Do not retain an unsafe optional flag path for convenience.
